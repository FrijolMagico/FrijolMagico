## Accepted behavior and current implementation
- DB failure keeps existing errors; DB success stays successful despite ordinary web synchronization failure. Such failures are internal logs only, not failed saves or UI warnings.
- Any requested SWR in an executed branch, including mixed batches and failed delivery, should append normal-success delay copy without guaranteed timing. Immediate-only/no-effect retains existing confirmation. UI copy is **not implemented yet**. Suggested copy: “Los cambios se guardaron correctamente. Pueden tardar en aparecer en la web.”
- Exact `festivales:critico` and `catalogo:artistas:slugs` default immediate; explicit protected SWR is rejected before fetch/invalidation. Other tags preserve their policies. Shared pure `resolveWebRevalidationMode` lives in the existing cache-tags constants module. Handler immediate uses `revalidateTag(tag, { expire: 0 })`, SWR uses `max`; preserve action `updateTag`.
- `revalidateWebCache` remains throwing. BestEffort uses the same engine, captures/logs failures and returns Promise<void>. Exported request interface is available for typed caller arrays.
- New `revalidateWebCacheBatch(requests, context?: string)` filters no-effect entries, concurrently awaits independent operations via Promise.all, captures per-entry errors and returns optional `{ webRevalidation: 'swr' | 'immediate' }`; empty batch returns `{}`. Summary expresses requested policy, **not delivery success**.
- Transport: five-second budget per operation, maximum two attempts, no backoff. Retry network/timeouts/HTTP 408/429/5xx only; configuration/other HTTP/malformed or unconfirmed response failures are not retried. First attempt reserves part of remaining time for the second. Expired deadlines do not start/count fetches; late success is rejected; timers are cleared.
- This is **not enqueue/durable scheduling**. No concurrency limit, Retry-After handling, attempt-history/result array, deduplication or exactly-once/transaction guarantee. A timeout or partially applied tag+path request can cause repeated invalidation; retries repeat the failed entry, not the entire batch. No DB mutation is retried. These limitations were explained and current design approved; do not silently add infrastructure.
- Final failures use sanitized server console.error with `[web-invalidation]`, operation/tag/mode/category/status/timing/attempts. Recovered first-attempt failures have no retained history. Local visibility: admin terminal; after deployment: admin project's Vercel Runtime Logs. No browser-console/DB/file logging, raw errors, URLs, response bodies or secrets. This implementation is not deployed.
